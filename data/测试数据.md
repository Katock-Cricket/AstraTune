# 测试数据

从 BIRD-CRITIC 摘出的相关测试用例，用于调试。在 `scripts/` 下执行。

CLI 分工：
- `diag.py`：仅诊断
- `opt.py`：仅优化（需 `--diagnosis` / `--diagnosis-file`）
- `infer.py`：诊断 → Generate–Verify 端到端

**数据库版本：MySQL 8.4.0**

**数据库ID：debit_card_specializing**（加 `--dialect mysql --db-id debit_card_specializing`）

```shell
python diag.py --dialect mysql --db-id debit_card_specializing --sql "SET @current_time = TIMESTAMP('2022-12-01 12:40:00');WITH cte AS (SELECT slot, SUM(total) OVER(ORDER BY slot) AS total, total AS rowtotal FROM sales WHERE slot < @current_time ORDER BY slot DESC LIMIT 1) SELECT total - (30 - TIMESTAMPDIFF(MINUTE, slot, @current_time))/30 * rowtotal AS total FROM cte" --preprocess-sql "CREATE TABLE sales (id INT, slot TIMESTAMP, total INT);INSERT INTO sales VALUES(1, '2022-12-01T12:00', 100), (2, '2022-12-01T12:30', 150), (3, '2022-12-01T13:00', 200);CREATE INDEX idx_test ON sales (slot);" --clean-up-sql "SET @current_time := NULL;DROP TABLE sales;" --user-prompt "Suppose we have a transactions data table within an e-commerce platform that records purchases made by various customers at different gas stations. The table 'sales' is like |id|slot|total|
There's an index on slot already. I want to sum the total up to the current moment in time (EDIT: WASN\'T CLEAR INITIALLY, I WILL PROVIDE A LOWER SLOT BOUND, SO THE SUM WILL BE OVER SOME NUMBER OF DAYS/WEEKS, NOT OVER FULL TABLE). The hardcoded 30 would not work in that case.The platform tracks the sales forecasts for gas products, which are recorded in half-hour time slots. **数据库版本：PostgreSQL 14.1**
```

**数据库ID：financial**

### 诊断 `diag.py`

```shell
python diag.py --db-id financial --sql "SELECT t.trans_id,       t.account_id,       t.date,       t.type,       t.amount  FROM trans t  JOIN account a    ON t.account_id = a.account_id WHERE a.district_id = 18   AND t.bank = 'AB'  AND t.type IN ('PRIJEM', 'VYDAJ');" --user-prompt "We have a large transaction table in our financial database with over 180 million rows and 20 GB in size. The table is structured to store detailed transaction records for various accounts. We are running a query to retrieve specific transactions based on a list of account IDs, a specific bank, and a range of transaction types. The query is taking an unexpectedly long time to execute when the shared buffers are cold, around 9 seconds, but only 25 ms when the data is cached. We suspect that the query planner is not choosing the most optimal execution plan. We have tried adding a covering index and forcing a Bitmap Heap Scan, but we would like to understand why the planner is not making the best choice and find a more permanent solution to improve performance to around 1-2 seconds."
```

```shell
python diag.py --db-id financial --sql "select * from trans where date_part('month', 'date') = date_part('month', now()) and date_part('day', 'date') = date_part('day', now()) order by 'date' desc;" --preprocess-sql "CREATE INDEX ix1 ON trans (EXTRACT(MONTH FROM date), EXTRACT(DAY FROM date));" --clean-up-sql "drop index if exists ix1;" --user-prompt "I am trying to speed up a PostgreSQL query to find previous transactions on the same day of the year from the 'trans' table. My current query is as follows:\nsql \nselect * from trans \nwhere date_part('month', date) = date_part('month', now()) \nand date_part('day', date) = date_part('day', now()) \norder by date desc; \n\nThis query works but is running much slower than desired. Is there a better approach for comparing the current month and day?\nThe data is time-series in nature, and I am using PostgreSQL as the database."
```

### 优化 `opt.py`（需诊断结论；可先 `diag.py` 再粘贴）

```shell
python opt.py --db-id financial --category Efficiency --sql "SELECT t.trans_id, t.account_id, t.date, t.type, t.amount FROM trans t JOIN account a ON t.account_id = a.account_id WHERE a.district_id = 18 AND t.bank = 'AB' AND t.type IN ('PRIJEM', 'VYDAJ');" --user-prompt "We have a large transaction table... cold shared buffers ~9s, cached ~25ms; want ~1-2s." --diagnosis "【诊断结论】根因：planner 倾向对 bank='AB' 做 Bitmap Heap Scan，冷缓存随机 IO 大；应优先用 district_id 驱动 Nested Loop，并为 trans(account_id, bank, type) INCLUDE (trans_id, date, amount) 建覆盖索引。" --output ../outputs/opt_smoke.json
```

也可把诊断结论写入文件后：

```shell
python opt.py --db-id financial --category Efficiency --sql "SELECT t.trans_id, t.account_id, t.date, t.type, t.amount FROM trans t JOIN account a ON t.account_id = a.account_id WHERE a.district_id = 18 AND t.bank = 'AB' AND t.type IN ('PRIJEM', 'VYDAJ');" --diagnosis-file ../outputs/diag_report.txt --output ../outputs/opt_from_file.json
```

### 端到端 `infer.py`

```shell
python infer.py --db-id financial --category Efficiency --sql "SELECT t.trans_id, t.account_id, t.date, t.type, t.amount FROM trans t JOIN account a ON t.account_id = a.account_id WHERE a.district_id = 18 AND t.bank = 'AB' AND t.type IN ('PRIJEM', 'VYDAJ');" --user-prompt "We have a large transaction table in our financial database with over 180 million rows and 20 GB in size. The query is slow when shared buffers are cold (~9s) but fast when cached (~25ms). We want a permanent plan to reach ~1-2s." --output ../outputs/infer_smoke.json
```

快速跳过诊断、只验证优化链路：

```shell
python infer.py --db-id financial --category Efficiency --skip-diagnosis --sql "SELECT t.trans_id, t.account_id, t.date, t.type, t.amount FROM trans t JOIN account a ON t.account_id = a.account_id WHERE a.district_id = 18 AND t.bank = 'AB' AND t.type IN ('PRIJEM', 'VYDAJ');" --user-prompt "cold buffer slow query on financial.trans" --output ../outputs/infer_skip_diag.json
```
