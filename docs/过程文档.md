## 1. 项目背景与目标

### 1.1 研究背景

AstraTune 是一种基于大模型与多智能体协同的数据库慢查询诊断与优化方法。研究内容以卫星互联网为应用场景，但实际实现面向更广泛的 SQL 问题解决，最终以 BIRD-CRITIC Benchmark 作为实验验证基准。

### 1.2 总目标（GOAL）

1. **诊断智能体**：ReAct + 沙箱 — **已调通**
2. **修复多智能体**：Generate–Verify（无 Reflect）— **已完成**
3. **BIRD-CRITIC 实验验证**：**PG 530 正式全量 51.13%（271/530）**；Open-MySQL ~100 仍延后
4. **WebUI**：单条全流程演示 — **延后（P2）**

### 1.3 已确认的需求调整

| 原定模块 | 决策 | 说明 |
| ---- | ---- | ---- |
| 微调数据集 / Qwen3-32B | **砍掉** | 基座 API（当前 `deepseek-v4-flash`） |
| RAG / 经验库 | **砍掉** | 勿恢复 |
| Reflect / 知识沉淀 | **已删除** | 失败由 Verify `failure_reasons` 回灌 Generate |
| 达梦（DM） | **冻结** | `NotImplementedError` |
| 卫星互联网领域限定 | **泛化** | 通用 SQL |
| Verify DDL/DML 硬拦 | **已取消** | 安全靠沙箱隔离 |

### 1.4 评测范围确认

- **方言**：PostgreSQL + MySQL（均需支持）
- **当前验收集**：BIRD-CRITIC **PG 530** — **正式评测 51.13%（271/530）**；报告 `docs/pg530评测报告.md`
- **下一步（慢 SQL 专项）**：[Diff-SQL](https://github.com/L-nshpp/Diff-SQL) / **Effi-SQL 性能评测** — 面向 SQL 效率优化；代码以根目录 submodule `Diff-SQL/` 接入，**自带独立 Docker**（与 AstraTune `docker/`、BIRD `benchmark/evaluation` **三套互不合并**）；对接与跑批尚未开始
- **延后**：Open-MySQL ~100
- **Category**（BIRD-CRITIC）：Query / Management / Personalization / Efficiency（PG530 题面无 Efficiency）
- **评测机制（BIRD）**：官方 `benchmark/evaluation/src` wrapper；数据在 `benchmark_data/`
- **评测机制（Diff-SQL / Effi-SQL）**：走 `Diff-SQL/` 内评测脚本与其 Docker（patch / end2end）；详见 `Diff-SQL/README.md` 与 `docs/环境搭建.md` §5

## 6. 环境搭建（摘要）

完整步骤见 `docs/环境搭建.md`。

```bash
conda activate at
cd docker && docker compose --env-file stack.defaults.env up -d --build
```

配置：`config/agents.json`（`llm_key_mode=auto`，`llm_workers=4`，`instance_timeout_s=2400`）。

### PG 530（当前主跑批）

完整命令与前置校验见 **`docs/评测对接.md` §3**。摘要：

```bash
python scripts/check_sol_alignment.py \
  --schema benchmark_data/schema/post_schema.jsonl \
  --input benchmark_data/input/post/pg-00000-of-00001.jsonl \
  --sol benchmark_data/sol/pg_sol/pg_sol.jsonl \
  --report outputs/pg_align_report.json --require-pred-fields

python scripts/run_bird_critic.py \
  --schema benchmark_data/schema/post_schema.jsonl \
  --input benchmark_data/input/post/pg-00000-of-00001.jsonl \
  --dialect postgresql --output outputs/pg530_pred.jsonl \
  --resume --workers 4 --mode diag+opt --force-batch

python scripts/merge_pred_with_sol.py \
  --pred outputs/pg530_pred.jsonl \
  --sol benchmark_data/sol/pg_sol/pg_sol.jsonl \
  --output outputs/pg530_eval_ready.jsonl --require-pred

python scripts/run_official_eval.py \
  --dialect postgresql --jsonl outputs/pg530_eval_ready.jsonl --num_threads 2
```

进度：对 `outputs/pg530_pred.jsonl` 行数去重统计，或 `python scripts/slim_pred_jsonl.py --path outputs/pg530_pred.jsonl` 瘦身。跑批前确认 D: ≥30–50GB 空闲（见 `AGENTS.md` Docker 磁盘节）。

## 9. 开发注意事项

1. **LLM**：`OPENAI_API_KEYS`（`;`）或 `OPENAI_API_KEY`；`llm_key_mode=auto`；与 `--workers` 沙箱槽独立。
2. **批跑**：默认 `--isolate subprocess`；勿改回 inproc 跑全量。
3. **推理不喂 sol**；merge 阶段才合入。
4. **评测 `--limit`**：省略=全量；见 `docs/评测对接.md` §2.1。
5. **Docker 磁盘**：跑批前确认 D: ≥30–50GB。
6. **StreamHandler**：批跑模式截断工具/LLM 日志，避免管道撑死。
